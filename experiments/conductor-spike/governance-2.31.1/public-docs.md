## 2. Documented mechanism, assembled

**Configuration surface.** An administrator manages MCP governance in the **Kiro console** (the Kiro service in the AWS console) under **Settings → Shared settings**. Two controls: the **Model Context Protocol (MCP)** on/off toggle, and the **MCP Registry URL** field (choose **Edit**, paste URL, **Save**). Both are attributes of a **Kiro profile**, which is per AWS account + Region; profiles exist at organization level and account level, and the account-level profile supersedes the organization-level one — the documented example is "disable MCP for the organization but enable it with an allow-list for certain teams (accounts)". A second, file-based channel exists for adjacent controls: **`managed-settings.json`** at OS-protected paths (`/Library/Application Support/Kiro/`, `C:\ProgramData\Kiro\`, `/etc/kiro/`), deployed by MDM/GPO/SCCM, carrying permission `rules` (including `capability: "mcp"`, effects `deny`/`ask` only) and `signin_method` rules. The docs call the profile/console channel "enterprise governance" and warn it is *client-side enforced and circumventable with administrative access to the machine*.

**Who is governed.** Only users authenticating with **IAM Identity Center or API keys**; "Builder ID and social auth users are not subject to organization-level MCP controls." So MCP governance is an account/identity-class feature, not an on-device feature — except the managed-settings.json channel, which is per-device and version-gated (IDE ≥ 1.2, CLI ≥ 2.25.0).

**Plan tiers.** `/docs/mcp/registry.md` frames registry mode for "Pro-tier customers using IAM Identity Center" and "enterprise teams"; `/docs/billing.md` lists Free/Pro/Pro+/Pro Max/Power (no Teams/Enterprise tier named there; enterprise administration is described via Kiro profiles and subscriptions). No page states that MCP registry requires "Kiro Enterprise" branding; the literal tier claim is only "Pro-tier".

**State machine the docs describe.**
1. *Default (no governance)*: any MCP server may be used.
2. *MCP Off*: client suppresses **user-configured, legacy, registry, and session-injected** servers; `/mcp` shows `MCP has been disabled by your administrator`; no MCP tools reach the agent.
3. *Governance API unreachable*: MCP fails closed; `/mcp` shows `Failed to retrieve MCP settings — MCP disabled`. No documented last-known-good caching for the toggle itself.
4. *Registry active*: the allow-list is the **only** source of runnable servers. Registry is fetched **at startup and every 24 hours** over HTTPS (trusted CA; self-signed unsupported; corporate-private URL allowed). On sync: servers absent from the registry are **terminated** and **cannot be re-added**; version mismatches cause a **relaunch at the registry version**. Local `mcp.json` entries load **only if their name matches a registry entry**; everything else is hidden ("N servers hidden" in the IDE); users must ask an administrator to add servers. `kiro-cli mcp add`, `--name`, and `/mcp add` list/select only registry servers, and `/mcp add|remove` persist into the agent config.
5. *Over rides on registry entries*: URL/identifier/runtimeArguments/etc. are read-only; users may add `env` (local) or `headers` (remote), `timeout`, scope (Global/Workspace/Agent Configuration), and tool trust permissions; `env`/`headers` merge per-key with user values winning. Documented config form: an `mcp.json` entry with `"type": "registry"`.

**Registry file.** JSON, a subset of the MCP registry standard v0.1: `{"servers":[{"server":{…}}]}` where a server declares required `name`/`description`/`version` and at most one of `remotes` (`streamable-http` or `sse`, with optional `headers`) or `packages` (`registryType` npm|pypi|oci, `identifier`, optional `registryBaseUrl`, `runtimeArguments`, `packageArguments`, `environmentVariables`, transport `stdio`). Version ranges are rejected. Local servers run through `npx`/`uvx`/`docker`, which "must be pre-installed" on client machines.

**Bypass posture.** The docs are explicit: both MCP toggle and registry are **client-enforced** and "can be circumvented by users, e.g., via administrative access to their local machine". The registry page nonetheless states users "Cannot add custom servers". These are not in conflict: registry mode blocks the normal UI/config path, while the warning concedes a machine-level adversary can bypass the client. No server-side enforcement of MCP settings is documented. The permission-policy file adds an OS-level file-protection layer *for permissions*, and managed updates adds an analogous Windows-registry/GPO layer *for version pinning* (`UpdateUrl`), but neither is documented as being able to lock the MCP toggle itself. **AppLocker is never mentioned.**

**Surface gaps.** Kiro Web sessions explicitly ignore "MCP registry URL and other administrator MCP settings" (configure Web MCP in sandbox settings or repo `.kiro/settings/mcp.json`); the enterprise governance page repeats that "MCP configuration … do[es] not apply to Kiro Web sessions".

## 3. Open questions (need live probes; not answerable from public docs)

1. **Registry-fetch failure semantics.** Docs specify fail-closed for the *governance API* (toggle path). What happens when the registry URL itself is unreachable/malformed after a successful governance fetch — MCP disabled, last-fetched registry retained, or servers left running? No documented statement. Probe: point a 2.31.x client at an unreachable registry URL and observe `/mcp`.
2. **Toggle vs registry precedence.** Is "MCP Off" evaluated server-side (governance API returns disabled) or merely reflected from the same API? The client-visible behavior is documented, the wire mechanism is not.
3. **Name-match semantics.** Registry gating of local `mcp.json` entries is by "name matches"; case-sensitivity, aliasing, and collisions (two entries, same name) are undocumented. Probe by defining a same-name server locally.
4. **Session-injected vs registry.** Session-injected servers are suppressed when MCP is *off*; whether an injected server that does not name-match a registry entry can run while the registry is active is undocumented. Probe with `/mcp add` and a power-installed server.
5. **Tier enforcement reality.** "Pro-tier customers using IAM Identity Center" vs the org/account-profile framing: whether a Free or Builder-ID-anchored org can configure the registry, and what a non-Pro IdC org sees, is not documented. Probe console visibility per tier.
6. **Per-server access modes.** The docs describe a flat allow-list; no per-entry admin mode (disabled-but-listed, auto-approve, trust) is documented beyond the user-side trust/scope/override fields. Confirm no hidden per-server state exists in the 2.31.1 client (binary strings / wire evidence in sibling audits).
7. **AppLocker/managed-settings for MCP.** No AppLocker mention; whether `managed-settings.json` can carry an MCP-specific rule (e.g., force MCP off, pin registry URL) beyond `capability: "mcp"` ask/deny is undocumented. Probe: add unknown-field/`settings` keys and observe validation.
8. **CLI reference inconsistency.** `/docs/reference/cli-commands.md` documents `kiro-cli mcp add` with `--command` required and no registry flag, while `/docs/mcp/registry.md` documents `kiro-cli mcp add` (interactive registry picker) and `kiro-cli mcp add --name myserver`. Which forms exist in 2.31.1 (and how `--force`/`--command` interact with registry entries) needs a live `--help` check.
9. **Version pinning mechanics.** "Relaunches the server with the version defined in the registry" — whether that pins npm/pypi/oci package versions locally or triggers re-download is unspecified.
