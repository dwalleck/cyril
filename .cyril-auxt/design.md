## Behaviour

**Scope page.** Picking an `allow_always` option on a request that carries KAS metadata (`_meta.kiro`, typed as `PermissionConsent`) and no V2 `trustOptions` opens `Always Allow — Choose Scope` instead of answering — the TUI's `De` (KAS engine, no trust tiers). It opens at the scope the previous scope page last showed while approvals stay queued (`k2t` carries `trustScope`), and at `session` when a request arrives to an empty queue (the TUI's approval panel, which holds that state, is mounted only while an approval is pending — byte 13561339). It shows `capability → resource`, the scope line, and rows built from the consent:

| Row | When | Echoed resource |
|---|---|---|
| `Trust "<gated>"` — `exact match · <scope>` | gated resource present and not `*` | gated resource |
| `Trust "<cmd> *"` — `pattern · <scope>` | shell capability, pattern differs from gated | `<cmd> *` |
| `Allow a folder <for this session \| in this workspace \| for your user>…` — `<prefill> · <scope>` | main session, capability `fs_write`, not `askType:"explicit"`, resource present, not `*`, no glob characters, not absolute when a workspace root is present, normalises without `..`, parent ≠ `.`; scope `workspace` only in a workspace, `user` only outside one, `session` always | `<folder>/**` |
| `Trust entire tool (<toolId>)` — `<scope>` | always | `*` |

`s` cycles the scope; the highlighted row is kept when it still exists (a folder row's label changes with scope, so it resets to the first row, as in the TUI). Esc returns to the option list.

**Folder entry.** Enter on the folder row opens a one-line editor prefilled with the parent folder. The status line is the TUI's live validation: valid → `Allows writes in <path> and every folder under it, <for this session only | in this workspace | for your user>.`; invalid → the TUI's reason, coloured as an error once Enter was pressed on it. Enter on a valid folder answers; Esc returns to the scope page.

**Response.** cyril answers the picked `allow_always` option id and the converter adds `_meta.kiro.consent{capability, scope, resource, workspaceRoot}` at the response's top level (where KAS reads it; T1). `capability` and `workspaceRoot` are copied verbatim from the request's own consent, as the TUI does. A non-main-session pick that cannot form a TUI child grant answers the request's allow_once option instead, without metadata (`C8n`).

**Waiting approvals.** After an "Always allow" answer, the approvals already queued behind it that the grant covers are answered at once with their own `allow_once` option and leave the queue; the rest keep their order. Coverage is the TUI's `k8n` exactly: on the main session only a whole-tool grant settles anything (same capability class — `shell`/`exec`/`shell:exec` fold together — same workspace root, same session); a grant recorded for another session (`_lt`) settles that session's queued requests it matches (`D4`). Exact, pattern and folder grants on the main session settle nothing (KAS itself decides the next ask). A covered request that offers no `allow_once` stays queued (the TUI would send a literal `"allow_once"` id; cyril never sends an id the request did not offer). No metadata rides these answers (user decision 2, below). No wire change: plain `allow_once` responses, already proven optional-echo for invocation scope (cyril-gn07, qo13 probe).

**V2 path on KAS.** The domain mediator forwards no V2 `trustOptions` on a KAS-engine request, so the agent-JSON `allowedCommands` write (`App::persist_trust_grant`) can only run for v2. v2 requests carry no `_meta.kiro` and keep their trust-tier flow unchanged.

## Placement

- **Owner `cyril-core::always_allow` (new module).** Pure domain: `GrantScope`, `GrantResource`, `AlwaysAllowGrant`, `ScopeChoice`, `FolderOffer`/`AllowedFolder`/`FolderError`, row derivation, folder validation, and the main/child resolution to a `PermissionResponse`. Forbidden: ACP types, JSON, UI concepts.
- **`review::consent::PermissionConsent`** gains the verbatim consent capability, `triggeringResource`, and `askType == "explicit"`, set in `convert/kas.rs::permission_consent` (the only `_meta.kiro` parser).
- **`types::PermissionResponse::AlwaysAllow { option_id, grant }`** — new variant; the existing `Selected` / `RejectWithReason` / `Cancel` keep their wire output.
- **`protocol/convert/kas.rs::attach_consent_echo`** builds `_meta.kiro.consent` from the request args and the typed grant (KAS wire owner; `mod.rs` only dispatches, `#[cfg(feature = "kas")]` like `attach_rejection_metadata`).
- **`protocol/domain_mediator`**: on KAS, `trust_options` = empty.
- **`cyril-ui`**: `ApprovalState.consent`; `ApprovalPhase::{SelectScope, EnterFolder}`; `UiState` transitions; `widgets/approval.rs` gains two render functions (no change to the existing option/trust/reason renderers, so cyril-q0kg / cyril-rcub rebase cleanly). The folder editor reuses `RejectionFeedback` (the approval's existing text editor) rather than a second editor.
- **`cyril` App**: routes `s` and the folder editor's keys/paste; no domain logic.

## Non-goals and future work

- **Invocation echo on allow_once / reject_once / reject_always — user decision 2 (deliberate divergence).** The TUI also echoes `scope:"invocation"` on those (`cw`); for reject_always that turns KAS's default session-scoped deny into a one-shot deny. The requester decided (2026-10-18, relayed by the coordinator): "KEEP cyril's behaviour (no echo on allow_once/reject_once/reject_always; "Always deny" stays KAS's session-wide deny)". The queue-release answers (allow_once) follow the same decision.
- **Stored child grants for later arrivals (not mirrored; scope decision pending).** Beyond the queue, the TUI keeps child grants (`kasChildConsentGrants`, `wlt`) and auto-answers approvals that ARRIVE later on that child session when `D4` matches (`Edt` → `iUn`, byte ~11476900; workspace/user-scope grants are consumed once; grants are dropped when their session ends, byte ~11433900). The requester asked for already-queued approvals only ("nothing broader"), so cyril does not keep grants; reported back as an open question.
- `persistableConsent:false` (cyril-k8wc) — prerequisite, separate PR #172; not touched. Under bash/zsh KAS offers no allow_always for shell commands until #172 lands (user decision 4 confirms this stands).
- **Sub-agent requests count as main-session requests (known divergence).** The TUI re-attributes a KAS permission request to its sub-agent subtask (`prepareKasPermissionRequest`, byte 10608706: `toolCallToSubtask.get(toolCallId)`, learned from `tool_call` frames tagged `_meta.kiro.agentSubtaskId`), so a sub-agent's approval gets no folder row and an exact `fs_write` grant is downgraded (`C8n`). KAS 0.66.43 does not put `agentSubtaskId` on the permission request itself (its `_meta.kiro` is `toolId, command, agentManagesTrust, disclosedContext, workflowWatch, workflowPlan, consent, consentRound, mcpTool`; `acp-server.js` ~byte 11482266), and cyril tracks no subtasks — that is cyril-ebqu (KAS crew rendering). Until then cyril applies the main-session rows to sub-agent approvals; the `_lt`/`C8n` rule is implemented and covers requests on other session ids (workflow steps). Independent review should-fix 1; the requester confirmed (2026-10-18) this divergence stands as described, tracked on cyril-ebqu.
- Whole-tool label uses `_meta.kiro.toolId` (the TUI uses its tool_use message name). Label text only; the echoed resource (`*`) is identical.
